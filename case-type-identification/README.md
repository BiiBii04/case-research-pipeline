# Case type identification (Tom's approach)

Eight Claude Skills, not method files: a classifier (`case-orchestrator`) plus one skill per case type it can hand off to (`case-brand-communication`, `case-profit-optimization`, `case-supply-chain`, `case-ma`, `case-product-launch`, `case-investment`, `case-market-entry`). The seven case-type skills are single-file: a checklist for recognizing that case type plus a condensed solving framework, in `SKILL.md`. This public copy deliberately excludes each skill's full worked framework detail and worked examples (kept in a team-private `references/` folder that never leaves the original author's machine) — what ships here is the checklist, the step-by-step roadmap, and enough of each formula/structure to follow, not a complete how-to. `case-orchestrator` is the exception: its `references/checklists.md` is included because that file is original synthesis this skill actively reads at runtime, not supplementary worked detail. `case-orchestrator` reads a brief, segments it into sub-questions, scores each against a condensed checklist, hands off to the matching skill, and integrates every sub-answer back into one structure tied to a shared objective.

This classify-then-solve shape is doing different work than the Frame through Defend stages, this could slot in around framing, run alongside the pipeline as an independent front door, or stay a separate tool entirely.
